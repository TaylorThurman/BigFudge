# Implementation Spec Skill

This skill produces a lean, reference-oriented implementation specification. The implementation spec is the "constitution" for the codebase — it defines module interfaces, coding conventions, project structure, and developer context. It is designed to be consulted during development, not read end-to-end as a build guide.

**This document should be concise.** Target 3,000–5,000 tokens. Every section should earn its place by reducing ambiguity about how to write code in this project. If a section doesn't help a developer make a correct decision while coding, it doesn't belong here.

## Where This Fits in the SDLC

This is **Phase 3** of the skill chain:

1. **Product Spec** — What are we building and why?
2. **Architecture Blueprint** — How is the system designed?
3. **Implementation Spec** (this skill) — What are the rules and interfaces for the codebase?
4. **Tickets** — What are the individual units of work?
5. **Test Plan** — How do we validate it?

The implementation spec consumes the architecture blueprint and produces the developer-facing reference needed to write consistent, interoperable code. It does NOT contain detailed build steps — those belong in individual tickets generated by the ticket skill. Think of this document as what goes in the CLAUDE.md and the project's contributing guide, not a project plan.

### What Belongs Here vs. Other Skills

**In this skill (developer reference):**
- Repo and code structure (directory tree, file purposes, import boundaries)
- Module interfaces and contracts (class hierarchies, method signatures, shared data structures)
- Code patterns and conventions (naming, error handling, logging, config access)
- Dependencies and environment setup
- CLAUDE.md / developer context
- Git workflow and branching strategy

**NOT in this skill:**
- Detailed build steps and implementation order (tickets)
- System design rationale (architecture blueprint)
- Test suites and validation criteria (test plan)
- Deployment procedures and CI/CD pipelines (tickets — as implementation work)
- Product requirements and scope (product spec)

---

## Core Principles

**Reference over narrative.** This is a document developers consult while working, not a story they read once. Optimize for quick lookup — clear headings, consistent formatting, code samples next to the rules they illustrate.

**Interfaces over implementations.** Define the contracts between modules (what they accept, what they return, what invariants they maintain) rather than dictating internal implementations. This gives developers freedom while maintaining system coherence.

**Concise over exhaustive.** Every section should be as short as possible while still eliminating ambiguity. If a convention can be stated in one sentence with one code sample, don't write a paragraph. Target 3,000–5,000 tokens for the entire document.

**Previous specs are sacred.** When a prior version exists, every detail must be accounted for. Nothing gets silently dropped.

---

## Handling Previous Specs

Before writing, determine whether a previous implementation spec exists.

### If a previous spec exists:

1. Read it completely before writing.
2. Inventory all existing content.
3. Merge forward — preserve everything unless explicitly changed.
4. Generate a Changelog.

### If no previous spec exists:

The architecture blueprint is the primary input. Read it thoroughly. If no blueprint exists either, gather enough information from the conversation to produce useful developer reference material — but suggest the user create an architecture blueprint first for best results.

## Section Details

### 1. Project Overview

A brief summary (1-2 paragraphs) orienting a developer who has read the architecture blueprint. What's the tech stack? What are the most important structural decisions? What are the biggest implementation risks? Keep this tight — the architecture blueprint has the full context.

### 2. Repo & Code Structure

A complete directory tree showing where everything lives. For each directory and key file, explain its purpose in a brief annotation. State the import boundaries (e.g., "shared/ must not import from domain-specific code").

```
project-name/
├── module-a/            <- [What this module does]
│   ├── core.py          <- [What this file contains]
│   └── helpers.py       <- [What this file contains]
├── module-b/
│   └── ...
└── README.md
```

Keep annotations to one line per entry. The directory tree is a map, not a narrative.

### 3. Module Interfaces & Contracts

The most important section. For each key module or class, define its interface — what it accepts, what it returns, and what guarantees it makes. Use code samples that show actual signatures and patterns.

This section is the contract that allows different parts of the system (and different tickets) to be built independently. Two developers working on different tickets should be able to read this section and produce code that connects correctly.

Include:
- Abstract base classes and their method signatures
- Key function signatures with parameter and return types
- Data structures / schemas that cross module boundaries
- Invariants that callers and implementers must respect

Keep code samples minimal — show the shape (signatures, types, docstrings) not the implementation.

### 4. Code Patterns & Conventions

The rules every contributor must follow. For each convention, state the rule and show one brief example.

Cover:
- Naming conventions (files, classes, functions, variables)
- Error handling approach (exceptions, return codes, result types)
- Logging conventions (format, levels, what to log)
- Config access patterns (how modules read their configuration)
- Testing expectations (every implementation includes tests that verify the ticket's acceptance criteria — the test plan defines tooling, conventions, and coverage targets)
- Any project-specific patterns (strategy pattern, observer, etc.)

One rule + one example per convention. No more.

### 5. Dependencies & Environment Setup

Everything needed to set up a working development environment:

- Runtime dependencies (with versions or version ranges)
- Development dependencies (linters, formatters, test tools)
- System-level dependencies (language version, OS requirements)
- Environment variables that must be set

Include the actual requirements file or package manifest content. A developer should be able to copy-paste this to get set up.

**Do NOT include deployment configs** (docker-compose, Dockerfiles, systemd units, launchd plists, CI/CD pipeline definitions). Those are implementation work handled through tickets.

### 6. Developer Context (CLAUDE.md)

The document that gives an AI developer (or a new human contributor) the rules and context needed to contribute safely. This should be directly usable as a CLAUDE.md file.

Include:
- Project purpose (one sentence)
- Key rules and constraints (what NOT to do)
- Common tasks and how to run them (build, test, lint)
- Testing rule: all implementations must include tests that verify the ticket's acceptance criteria, using the tooling and conventions defined in the test plan
- Files that should rarely be modified
- Debugging tips for common issues

This section should be self-contained — a developer reading only this section should be able to start working safely.

### 7. Git Workflow

How code moves from development to production. The following conventions are mandatory and must be included in every implementation spec:

- **Branch naming**: `feature/T-XXX-short-description` (e.g., `feature/T-003-zigbee-reader`). Every branch is tied to a ticket.
- **Commit messages**: `T-XXX: Description` (e.g., `T-003: Add Zigbee sensor reader with persistence`). Ticket ID prefix is mandatory.
- **PR titles**: `T-XXX: Description` — matches the commit message format.
- **PR/review process**: All PRs require human approval before merging to main. No auto-merge.
- **Main branch**: Always deployable. No direct commits — all changes go through feature branches and PRs.

Add any project-specific conventions beyond these defaults (e.g., squash vs. merge commits, required reviewers).

### 8. Open Questions

Implementation-specific unknowns — tooling choices, convention decisions, and practical concerns that need resolution before or during development.

### 9. Changelog

Always included, even for v1 initial drafts.

For v1 (initial draft):
```markdown
## Changelog

### v1 — Initial Draft
- Initial implementation spec created from [source: architecture blueprint vN / conversation / etc.]
- [Note any major assumptions or gaps]
```

For subsequent versions, use the standard Added / Changed / Removed / Clarified categories.

## Writing Guidelines

- **Show, don't just tell.** For interfaces and patterns, include actual code samples. A code sample is worth a paragraph of description.
- **Keep code samples minimal but complete.** Show enough to illustrate the signature or pattern — not full implementations. The purpose is to show the shape of the code.
- **Include the awkward details.** Environment variables, file permissions, OS-specific quirks, version pinning — the things that cause "it works on my machine" problems.
- **Aim for 3,000–5,000 tokens.** If you're exceeding this, you're probably including build steps or design rationale that belongs elsewhere. Cut aggressively.
- **No deployment configs.** Docker-compose files, Dockerfiles, systemd units, launchd plists, CI/CD pipelines, and similar deployment infrastructure are implementation work handled through tickets, not here.

## Output

Produce two files:

### 1. Implementation Spec
The implementation spec as a single Markdown file. Filename: `[project-name]-implementation-spec-v[N].md`

### 2. Project README
A populated top-level `README.md` for the project repository. This is the human-facing entry point — it should give someone unfamiliar with the project everything they need to understand what it is and how to work with it.

The README must include:
- **Project name and description** — What does this project do? (1-2 paragraphs)
- **Tech stack** — Languages, frameworks, databases, key libraries
- **Getting started** — How to install dependencies, set up the environment, and run the project locally
- **Project structure** — A brief directory overview (the implementation spec has the full annotated tree, but the README needs a readable summary)
- **Running tests** — The commands to run the test suite
- **Configuration** — What environment variables or config files are needed, with example values (no real secrets)
- **Contributing** — Brief guidance pointing to CLAUDE.md and the implementation spec for conventions

The README is written once during the initial implementation spec phase and updated when the implementation spec is updated. It is a living document — not a placeholder to fill in later.

Save both files and present them to the user.

The implementation spec output is consumed by downstream SDLC phases. Do not suggest or invoke the next skill — the SDLC router (or the user) determines what runs next. For context:
- **Tickets** — Uses the architecture blueprint and this implementation spec to produce individual, scoped work tickets that a coding agent or developer can pick up and execute.
